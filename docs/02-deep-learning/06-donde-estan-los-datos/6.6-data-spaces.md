# 6.6 Data spaces: las reglas del juego

> **El principio fundamental:** El aprendizaje federado resuelve el problema **técnico** de entrenar sin centralizar datos; los **Espacios de Datos (*Data Spaces*)** resuelven el problema **institucional, legal y de gobernanza**. Sin un espacio de datos soberano, dos organizaciones competidoras nunca colaborarán en el mundo real.

---

## 🧭 La intuición antes que la fórmula: soberanía vs. privacidad

Imagina que dos cadenas de inspección de vehículos (ITV) o dos hospitales quieren entrenar un modelo conjunto. Tienen datos valiosísimos, pero sufren dos miedos razonables:

1. **Miedo al robo/expropiación:** *"Si te envío mi dataset, pierdo el control para siempre."*
2. **Miedo al mal uso:** *"Te doy acceso para diagnosticar una enfermedad concreta, pero no para que comercialices un seguro sin mi permiso."*

El concepto clave que resuelve un Data Space es la **Soberanía de Datos (*Data Sovereignty*)**:

> **Soberanía:** El propietario del dato mantiene el control ejecutivo sobre para qué, quién, cuándo y bajo qué condiciones se procesa su información, **incluso después de haber otorgado acceso a terceros**.

A diferencia de la privacidad (ocultar la información), la soberanía consiste en **gobernar la ejecución del cómputo**. De ahí la máxima arquitectónica del área:

$$\text{\textbf{"El cómputo viaja al dato, nunca el dato al cómputo"}}$$

---

## 🏛️ Las Piezas de un Espacio de Datos Europeo (IDSA & Gaia-X)

Un Espacio de Datos no es una base de datos centralizada; es una **federación descentralizada de participantes soberanos** que comparten un marco de confianza común (*Trust Framework*).

```none
  [ Empresa A (Proveedor) ]  ◄── Dataspace Protocol (DSP) ──►  [ Empresa B (Consumidor) ]
      │                                                                  │
      ├── Conector Soberano (Eclipse EDC)                                 ├── Conector Soberano (Eclipse EDC)
      ├── Credencial Verificable (W3C DID)                               ├── Credencial Verificable (W3C DID)
      └── Custodia Local del Dato (On-Premise)                           └── Ejecución de Algoritmos
                                            │
                                            ▼
                        [ Catálogo Federado / Servicio de Cómputo ]
                        [ Contrato ODRL: Reglas de Uso Ejecutables ]
```

| Componente | Función | Tecnología / Estándar de Referencia |
|---|---|---|
| **Conector Soberano** | Agente de software que media cualquier intercambio de datos o cómputo, evaluando contratos en tiempo real. | **Eclipse EDC (Dataspace Components)**, IDS Connector. |
| **Identidad Descentralizada** | Identificación de participantes mediante claves criptográficas sin dependencias de un único servidor. | **W3C DIDs**, Verifiable Credentials (VCs). |
| **Catálogo Federado** | Publicación de meta-información sobre qué datos y servicios de cómputo existen, sin exponer los datos crudos. | Federated Catalog, Ocean Aquarius. |
| **Contratos y Políticas de Uso** | Especificación formal y legible por máquinas de los permisos, prohibiciones y obligaciones de uso. | **W3C ODRL 2.2** (Open Digital Rights Language). |
| **Interoperabilidad Semántica** | Ontologías compartidas para que dos sistemas entiendan exactamente qué significa cada campo. | FIWARE Smart Data Models, Vocabularios IDSA. |

## 🌊 Ocean Protocol & Compute-to-Data (C2D)

[Ocean Protocol](https://oceanprotocol.com) es una pila tecnológica de código abierto construida sobre arquitectura Web3 diseñada para tokenizar, monetizar y gobernar el acceso a datos y cómputo sin perder el control.

```none
   Algoritmo de Aprendizaje ──┐
                              ├─▶ [ Ocean Compute Engine (Pod K8s) ] ──▶ Solo Sale el Modelo Entrenado (pesos/métricas)
   Dataset Privado (On-Prem) ─┘   (Enclave aislado en el Proveedor)     (El dato crudo NUNCA abandona el servidor)
```

### El Mecanismo Compute-to-Data (C2D)
En lugar de descargar un archivo a través de una API HTTP, **Compute-to-Data** permite al consumidor enviar un algoritmo de entrenamiento (ej. un script de PyTorch o Flower) al servidor del proveedor:

1. El proveedor recibe la solicitud cifrada y verifica la política de acceso mediante tokens criptográficos (**Datatokens / Data NFTs**).
2. Se levanta un contenedor aislado (**Kubernetes Pod / Docker Enclave**) dentro de la infraestructura del proveedor.
3. El algoritmo se ejecuta localmente sobre los datos privados.
4. El contenedor se destruye tras exportar **únicamente las métricas o los gradientes actualizados**, manteniendo el dataset original completamente inalcanzable.

## ⚡ Pontus-X: El Espacio de Datos Industrial e Institucional

[Pontus-X](https://pontus-x.eu) es un espacio de datos descentralizado paneuropeo orquestado por **deltaDAO** en colaboración con la comunidad de **Ocean Protocol** y alineado con los principios de **Gaia-X**.

### Puntos clave de la arquitectura Pontus-X

- **Infraestructura de Red EVM Soberana:** Funciona sobre una red blockchain permisionada basada en Astar / Substrate, garantizando baja latencia, trazabilidad de auditoría y costes de transacción previsibles para empresas.
- **Cumplimiento Gaia-X Trust Framework:** Integración nativa de identidades institucionales mediante *Verifiable Credentials* (VCs) para asegurar que solo participantes verificados accedan a la red.
- **Liquidación Financiera en EUROe:** Soporte para la moneda estable en euros regulada por MiCA (**EUROe**), permitiendo la automatización de contratos inteligentes y facturación comercial B2B sin volatilidad cripto.
- **Orquestación de Aprendizaje Federado y C2D:** Permite a empresas de sectores como automoción (Catena-X), logística e inspecciones técnicas (ITV) monetizar y entrenar modelos sin transferir la propiedad del dato.

## 🔌 Eclipse Dataspace Components (EDC) / Eclipse Connectors

El proyecto [Eclipse Dataspace Components (EDC)](https://github.com/eclipse-edc/Connector) de la Fundación Eclipse representa la **referencia industrial de software libre** para la implementación de conectores de espacios de datos en Europa.

```none
                     ┌────────────────────────────────────────────────────────┐
                     │              CONECTOR ECLIPSE EDC                      │
                     ├───────────────────────────┬────────────────────────────┤
                     │   CONTROL PLANE           │   DATA PLANE               │
                     │   - Dataspace Protocol    │   - Transferencia HTTP/S3     │
                     │   - Negociación Contratos │   - Streaming Kafka            │
                     │   - Evaluación ODRL       │   - Túnel seguro C2D           │
                     └───────────────────────────┴────────────────────────────┘
```

### Arquitectura del Conector EDC

1. **Control Plane (Plano de Control):**
   - Implementa el **Dataspace Protocol (DSP)** para comunicarse con otros conectores.
   - Gestiona la autenticación mediante DIDs y Verifiable Credentials.
   - Ejecuta el motor de reglas de negociación de contratos de uso (**ODRL Engine**).
2. **Data Plane (Plano de Datos):**
   - Desacoplado del plano de control para escalar horizontalmente.
   - Realiza la canalización física de los datos (HTTP, S3, Azure Blob, Kafka, gRPC).
3. **Management API:**
   - Interfaz REST interna que permite a los sistemas ERP/CRM empresariales publicar ofertas de datos y consumir servicios.

## 📜 ODRL + Aprendizaje Federado: La Brecha de Investigación de la Tesis

**Open Digital Rights Language (ODRL 2.2)** es el estándar recomendado por el W3C para expresar contratos y licencias digitalmente.

### El Vacío en la Literatura Actual ⭐️
Las políticas ODRL tradicionales se diseñaron para acciones simples sobre archivos: `odrl:read`, `odrl:download`, `odrl:distribute`. **No existe una semántica estandarizada para traducir contratos ODRL a restricciones ejecutables sobre un algoritmo de Aprendizaje Federado / RL Offline.**

```none
  Contrato ODRL (JSON-LD)               Compilador de Políticas (Tesis)              Restricción en FL / RL
 ┌───────────────────────────┐         ┌────────────────────────────────┐         ┌────────────────────────────────┐
 │ Permiso: Train_ML_Model   │ ──────▶ │ Convierte reglas ODRL a        │ ──────▶ │ • Noise Differential Privacy  │
 │ Prohibición: Export_Raw   │         │ parámetros algorítmicos en     │         │ • Clipping de Gradientes (C)   │
 │ Obligación: Privacy_Eps≤2 │         │ el conector EDC / C2D          │         │ • Geofencing de nodos FL       │
 └───────────────────────────┘         └────────────────────────────────┘         └────────────────────────────────┘
```

### Ejemplo de Traducción de Política a Código

Una política ODRL expresada en JSON-LD:

```json
{
  "@context": "http://www.w3.org/ns/odrl.jsonld",
  "@type": "Offer",
  "permission": [{
    "target": "http://dataspace.itv.es/datasets/emisiones-2025",
    "action": "anonymizedTraining",
    "constraint": [{
      "leftOperand": "differentialPrivacyEpsilon",
      "operator": "lteq",
      "rightOperand": 2.0
    }]
  }]
}
```

Debe traducirse dentro del motor del conector en parámetros de entrenamiento federado:

$$\sigma_{\text{ruido}} = \frac{\sqrt{2 \ln(1.25/\delta)}}{\epsilon}, \quad C_{\text{clipping}} = 1.0$$

## ⚖️ El Marco Legal Europeo para Espacios de Datos

| Ley / Reglamento | Impacto en Arquitecturas de IA y Datos |
|---|---|
| **Data Governance Act (DGA)** | Regula los intermediarios de datos neutros y los espacios de datos altruistas. |
| **Data Act** | Obliga a garantizar el acceso y portabilidad de datos generados por dispositivos IoT. |
| **AI Act** | Exige gobernanza, trazabilidad y gestión de riesgos en datasets usados para entrenar IA. |
| **RGPD / GDPR** | Establece la distinción entre **Anonimización** (irreversible, sale del RGPD) y **Seudonimización** (reversible, requiere salvaguardas). |

## 🧪 Práctica recomendada para la Tesis

- [ ] **Despliegue local EDC:** Levantar un entorno local de dos conectores Eclipse EDC en Docker Compose y realizar una transferencia de prueba mediante el Dataspace Protocol (DSP).
