# 13.1 El mapa de decisiones

> **Qué responde:** ¿qué decisiones hay que tomar, en qué orden, y cuáles quedan
> cerradas por la restricción de C2D?

---

## Las seis decisiones

Un sistema de aprendizaje federado se define respondiendo a seis preguntas.
Igual que las tres de → 1.5, son en principio independientes, y en la práctica
unas condicionan a otras.

```none
① ¿QUÉ MODELO?          MLP · CNN · Transformer · árboles
② ¿QUÉ SE COMUNICA?     pesos · gradientes · adaptadores · logits · estadísticos
③ ¿CÓMO SE AGREGA?      FedAvg · FedProx · SCAFFOLD · destilación
④ ¿CUÁNTAS RONDAS?      una (one-shot) · pocas · muchas
⑤ ¿QUÉ SE PROTEGE?      nada · cegado · agregación segura · DP
⑥ ¿CÓMO VIAJA?          gRPC · ficheros · cola de jobs
```

**En C2D, la ⑥ está decidida de antemano: ficheros.** Y esa decisión aprieta
todas las demás.

---

## Lo que C2D cierra y lo que abre

| Decisión | Efecto de la restricción |
|---|---|
| ⑥ Transporte | **Cerrada.** Ficheros y jobs asíncronos (→ 11.1) |
| ④ Rondas | **Cara.** Cada ronda son K jobs. Empuja hacia one-shot (→ 13.5) |
| ② Qué se comunica | **Presionada.** Menos bytes = menos coste. Empuja a LoRA (→ 13.4) |
| ① Modelo | **Presionada.** El contenedor tiene límites de imagen y de tiempo |
| ③ Agregación | **Libre.** Cualquier agregador funciona: es matemática, no red |
| ⑤ Privacidad | **Libre y barata.** El cegado son 40 líneas (→ 12.2) |

Las dos últimas filas son buenas noticias: la parte donde hay más literatura y
más margen de contribución es precisamente la que la infraestructura no limita.

## El árbol de decisión práctico

```none
                  ¿el modelo es convexo?
                    │                │
                   SÍ                NO
                    │                │
              una ronda basta   ¿es un transformer preentrenado?
              (→ 12, → 13.5)      │                    │
                                 SÍ                    NO
                                  │                    │
                        LoRA federado           red desde cero
                        (→ 13.4)                       │
                                  │            ¿cuántos silos?
                        ¿rangos iguales?         │         │
                          │         │          pocos     muchos
                         SÍ        NO            │         │
                          │         │       FedProx    SCAFFOLD
                       FedAvg   FlexLoRA    (→ 13.3)   (→ 13.3)
                       de A·B    FLoRA
```

Y en paralelo, siempre: **¿cuánto cuesta esto en jobs?** Multiplica rondas por
silos antes de comprometerte con un diseño.

---

## La tabla de coste que conviene tener a mano

| Diseño | Jobs por ronda | Bytes por job |
|---|---|---|
| Sección 11 (FedAvg clásico) | K | tamaño del modelo |
| Sección 12 (FELT, doble ciego) | K + 1 | tamaño del modelo + overhead cripto |
| LoRA federado | K | **~0,1 % del modelo** |
| One-shot con destilación | K (+1) | modelo o dataset destilado |
| One-shot bayesiano | K | estadísticos, mucho menos |

Con un modelo de 7 000 M de parámetros, la diferencia entre enviar pesos
completos y enviar adaptadores LoRA es de tres órdenes de magnitud. **Esa fila
es la que hace viable o inviable el proyecto.**

---

## Un error de encuadre frecuente

Mucha gente ataca el problema como "¿qué framework de federado uso?". Es la
pregunta equivocada, o al menos la última.

El orden correcto:

1. **¿Qué modelo necesita el problema?** → condiciona todo lo demás.
2. **¿Cuánto puedo comunicar por ronda?** → decide si LoRA es obligatorio.
3. **¿Cuántas rondas me puedo permitir?** → decide si one-shot es obligatorio.
4. **¿Qué heterogeneidad tienen mis silos?** → decide el agregador.
5. **¿Qué hay que proteger, y de quién?** → decide la capa de privacidad.
6. **Y solo entonces:** ¿qué herramienta implementa esto con menos trabajo?

Elegir el framework primero es como elegir el optimizador antes de saber la
pérdida (→ 3.3).
