# 15.5 Lab 3 — El banco de pruebas

> **Estado: esbozo.** El script está escrito; no se ha lanzado ninguna tanda.
> Los cinco prompts propuestos son un punto de partida, no un conjunto validado.

## La pregunta

Las puntuaciones de [15.1](15.1-el-editor-y-su-configuracion.md) son
estimaciones ajenas sobre tareas ajenas. ¿Cuánto valen esos modelos **en mi
trabajo**?

## El diseño

El mismo prompt contra N modelos. Se mide lo automatizable y se juzga a mano lo
que no lo es.

| Se automatiza | Se juzga a mano |
|---|---|
| Latencia (ms) | Calidad de la respuesta (1-5) |
| Tokens de salida | Si hay que repetir la petición |
| Coste en dólares | Si inventa API que no existen |
| Errores y timeouts | Si respeta el estilo del proyecto |

La columna de calidad **se deja vacía a propósito** en la tabla generada. Ese es
el punto del laboratorio: la parte cara del trabajo es leer las salidas, y no
hay atajo. Un juez automático (otro modelo puntuando) parece tentador, pero
introduce el sesgo del juez justo en la medida que se quiere obtener.

## El script

Está en `labs/llm-lab/bench/run_bench.py`. Lee cada `.txt` de `prompts/`, lo
lanza contra la lista de modelos y escribe dos ficheros por prompt: el JSON con
las respuestas completas y una tabla en Markdown lista para rellenar.

```python
def coste(modelo: str, uso: dict) -> float:
    ent, sal = PRECIOS.get(modelo, (0.0, 0.0))
    return (uso.get("prompt_tokens", 0) * ent
            + uso.get("completion_tokens", 0) * sal) / 1e6
```

Los modelos `:free` no están en `PRECIOS`, así que caen en el `(0.0, 0.0)` por
defecto y su coste sale cero. Correcto, pero engañoso: **el coste de un gratuito
no es cero, es la cuota consumida**. Con 200 peticiones diarias por modelo, una
tanda de siete prompts contra siete modelos gasta el 3,5 % del día. Conviene
anotarlo como columna aparte cuando se automatice el seguimiento.

## Los prompts

Cinco, sacados de trabajo real del laboratorio y no de benchmarks públicos:

| Fichero | Tarea | Qué discrimina |
|---|---|---|
| `refactor.txt` | Una función fea del `dl-lab` y «refactorízala explicando por qué» | Capacidad de justificar, no solo de reescribir |
| `bug.txt` | Un traceback real y «encuentra la causa» | Razonamiento causal sobre código ajeno |
| `explicar.txt` | Un bloque de federado y «explícalo a alguien que sabe Python pero no ML» | Calibración del nivel de la audiencia |
| `docs.txt` | «Escribe la página tipo *explicación* de Diátaxis para este módulo» | Seguir una convención de estilo dada |
| `traducir.txt` | Un párrafo técnico del inglés al castellano | Terminología técnica sin calcos |

Que salgan de trabajo real importa: los benchmarks públicos llevan años en los
datos de entrenamiento, y un modelo puede puntuar alto en SWE-bench y fallar en
el estilo concreto de un proyecto.

## Cómo se usa

```bash
cd labs/llm-lab/bench
export OPENROUTER_API_KEY=sk-or-v1-...
python run_bench.py
```

Genera `resultados/refactor.md` con la tabla y `resultados/refactor.json` con
las respuestas completas. Se leen las salidas, se rellena la última columna y
esa tabla ya vale más que las estimaciones de 15.1.

## Qué se espera encontrar

Hipótesis a falsar, anotadas antes de mirar los datos para no engañarse después:

1. **El salto de 3/5 a 4/5 se nota; el de 4/5 a 5/5, poco.** Si es cierto,
   DeepSeek V4 Pro se queda como modelo por defecto y el gasto baja un orden
   de magnitud.
2. **Los gratuitos fallan antes en tareas largas que en tareas difíciles.**
   La longitud del contexto pesa más que la complejidad del razonamiento.
3. **En traducción y documentación la diferencia entre niveles casi desaparece.**
   Si se confirma, esas tareas se enrutan al barato siempre
   ([15.4](15.4-lab2-el-router-propio.md)).

La tercera es la que más ahorraría, porque documentar es una parte grande del
trabajo en este proyecto.

## Extensión natural

Añadir el modelo propio del [Lab 4](15.6-lab4-un-modelo-de-lenguaje-propio.md) a
la lista, no para que compita, sino para **ver el suelo**. Un transformer de 10M
de parámetros entrenado con el Quijote respondiendo a «refactoriza esta función»
enseña, de un vistazo, la distancia real entre saber imitar un idioma y saber
programar.
