## Una imagen, dos algoritmos

La decisión de FELT que replicamos: **el mismo contenedor sirve para las dos
fases**. Lo que cambia es el comando.

```dockerfile title="labs/felt-c2d/docker/Dockerfile"
FROM --platform=linux/amd64 python:3.12-slim

WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY src/ /app/src/
COPY algorithms/ /app/algorithms/
ENV PYTHONPATH=/app/src

# Sin ENTRYPOINT: el comando decide qué algoritmo se ejecuta
CMD ["python", "/app/algorithms/local_algorithm.py", "--help"]
```

**Nada de `ENTRYPOINT`.** Si lo fijas, el nodo no puede elegir el algoritmo, y
necesitarías dos imágenes casi idénticas. FELT publica una sola.

---

## `--platform=linux/amd64` no es opcional

El fallo número uno de quien desarrolla en un portátil con Apple Silicon:

```none
construyes en arm64  →  publicas  →  el nodo intenta ejecutar  →  exec format error
```

El mensaje no dice "arquitectura equivocada". Dice algo genérico, y puedes perder
una tarde. Construye siempre con `buildx` y plataforma explícita:

```bash
docker buildx build --platform linux/amd64 -t usuario/feltc2d:0.1 -f docker/Dockerfile .
```

---

## Publicar por digest, no por tag

Los tags son mutables: `usuario/feltc2d:latest` puede apuntar a otra cosa mañana,
y tu experimento de la semana pasada deja de ser reproducible.

```bash
docker push usuario/feltc2d:0.1
docker inspect --format='{{index .RepoDigests 0}}' usuario/feltc2d:0.1
# usuario/feltc2d@sha256:abc123...
```

Publica el **digest** en el asset de Ocean. Es la única forma de que el registro
del experimento sea trazable (→ 3.9).

## El test de contrato

La idea, igual que en → 11.4: no probar el algoritmo —eso ya lo hacen los tests
del Lab 0— sino que **la imagen cumple lo que el nodo espera**.

Un test de contrato monta carpetas de entrada y salida, ejecuta el contenedor
como lo haría el nodo, y comprueba que:

- [ ] El proceso termina con código 0.
- [ ] Aparece un fichero llamado exactamente `model` en la carpeta de salida.
- [ ] El contenido es descifrable con la privada correspondiente.
- [ ] Funciona con UID no-root.
- [ ] Funciona **sin red**: `docker run --network=none`.

Ese último es el importante. Si tu algoritmo necesita descargar algo en tiempo de
ejecución, morirá en el nodo real (→ 11.1) y el error no será obvio.

```bash
docker run --rm --network=none \
    -v "$PWD/trabajo/nodo0/inputs:/data/inputs:ro" \
    -v "$PWD/trabajo/nodo0/outputs:/data/outputs" \
    usuario/feltc2d:0.1 \
    python /app/algorithms/local_algorithm.py --aggregation_key <hex> --seed 1001
```

## El tamaño importa

El nodo descarga la imagen antes de ejecutar el job. Una imagen de 3 GB con
TensorFlow tarda, y algunos entornos de cómputo tienen límite.

| Imagen | Tamaño aproximado |
|---|---|
| Este laboratorio (NumPy + PyNaCl) | ~150 MB |
| Con scikit-learn | ~400 MB |
| Con TensorFlow | ~1,5 GB |

Es una de las razones por las que el laboratorio usa NumPy puro: no es purismo,
es que la iteración es mucho más rápida.
