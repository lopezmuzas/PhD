# 12.4 Lab 1 · Dos algoritmos, dos jobs

> **Qué responde:** ¿funciona el protocolo cuando cada fase es un proceso
> separado que solo se comunica por ficheros?

El Lab 0 pasaba objetos de Python entre funciones. Eso oculta el problema real:
en C2D, cada fase es un **contenedor distinto** que arranca, lee de disco,
escribe en disco y muere. Este lab añade exactamente esa variable.

```bash
make lab1
```

---

## Lo que cambia respecto al Lab 0

| | Lab 0 | Lab 1 |
|---|---|---|
| Comunicación | objetos en memoria | **ficheros en disco** |
| Ejecución | una función | **procesos separados** |
| Los pesos | `dict` de NumPy | JSON serializado y cifrado |
| Parámetros | argumentos de función | `algoCustomData.json` y flags |

Nada del algoritmo cambia. Cambia el **transporte**, que es donde se rompen las
cosas.

## El árbol que se genera

```none
trabajo/
├── nodo0/
│   ├── inputs/did:op:0000...0000/datos.csv    ← el dataset del proveedor
│   └── outputs/model                          ← salida cifrada del job
├── nodo1/ ...
├── nodo2/ ...
└── agregacion/
    ├── inputs/algoCustomData.json             ← {"model_urls": [...]}
    └── outputs/model                          ← el global, aún cegado
```

**Fíjate en la asimetría.** Los jobs de entrenamiento reciben *datos* en
`inputs/<DID>/`. El job de agregación no recibe datos: recibe **rutas a las
salidas anteriores** por `algoCustomData.json`. Es un job C2D que no toca ningún
dataset.

En Ocean real, esas rutas son URLs firmadas a las salidas de los jobs previos, y
el algoritmo las descarga. Aquí son rutas locales, que es la única diferencia.

---

## Los dos algoritmos

Se ejecutan por línea de comandos, igual que dentro del contenedor:

```bash
# uno por proveedor de datos
python algorithms/local_algorithm.py \
    --input_folder  trabajo/nodo0/inputs \
    --output_folder trabajo/nodo0/outputs \
    --aggregation_key <pública en hex> \
    --seed 1001 --modelo lineal

# uno solo, al final
python algorithms/aggregation_algorithm.py \
    --input_folder  trabajo/agregacion/inputs \
    --output_folder trabajo/agregacion/outputs \
    --private_key <privada en hex>
```

Los valores por defecto de `--input_folder` y `--output_folder` son `/data/inputs`
y `/data/outputs`: dentro del contenedor no hace falta pasarlos. Poderlos
sobreescribir es lo que permite ejecutar el lab en tu portátil.

---

## Los tres fallos que vas a cometer

### 1. El fichero de salida no se llama `model`

Es el más común y el más silencioso: el job termina en verde y el siguiente
eslabón no encuentra nada. El nombre es fijo y no negociable.

### 2. Perder las semillas

Las semillas viven **solo en tu orquestador**. No están en el modelo cifrado, no
están en el global, y no hay forma de recuperarlas. Si las pierdes entre el paso
2 y el paso 4, el modelo global es irrecuperable.

En el laboratorio esto se ve claro porque `run_lab1.py` las tiene en una lista.
En producción es un problema de gestión de estado con nombre propio.

### 3. Olvidar que `α` viaja con el modelo

Si construyes tú el JSON del modelo global y omites el campo `alfa`, la fase 3
resta la media simple y el resultado es basura — y **solo si los nodos tienen
tamaños distintos** (→ [12.2](12.2-el-protocolo-de-doble-ciego.md)).

## Del Lab 1 al nodo real

Lo que falta para llegar a un `ocean-node`:

| Paso | Dónde está documentado |
|---|---|
| Empaquetar los algoritmos en una imagen `amd64` | [12.5](12.5-lab2-el-contenedor.md) |
| Publicar la imagen como asset de algoritmo en Ocean | Documentación de Ocean |
| Que el proveedor autorice tu algoritmo sobre su dataset | Documentación de Ocean |
| Lanzar los jobs y encadenar sus salidas | → 11.5, el mecanismo es el mismo |
| Firmar las peticiones | → 11.6 |

**No repetimos el Lab 3 aquí.** Contra un nodo real, el procedimiento es
idéntico al de la sección 11: lo único distinto es que lanzas K+1 jobs en vez de
K, y que el último recibe rutas en lugar de datos.
