# 7.3 Offline RL + Federado + Data Spaces (La Pila Completa)

> **La celda central de la tesis:** Entrenar políticas de Deep Reinforcement Learning en modo **offline**, de forma **federada** entre múltiples proveedores de datos soberanos, coordinados por la capa de gobernanza de un **Data Space** (Gaia-X / IDS) sobre la infraestructura de **Ocean Protocol / Pontus-X**.

---

## 🎯 Por qué esta combinación exacta

No es una elección estética ni arbitraria: cada capa viene forzada inexorablemente por la anterior.

```none
En un Data Space real ninguna empresa permite exploración en vivo en sus sistemas
   └─► Solo existen registros históricos (logs) ............. ① OFFLINE RL (CQL, IQL)
        └─► Esos datos pertenecen a competidores o silos que NO los comparten
             └─► Cómputo local sin mover los datos ......... ② APRENDIZAJE FEDERADO (FL)
                  └─► Requiere reglas, identidades, contratos e incentivos
                       └─► Infraestructura de gobernanza ... ③ DATA SPACES (Gaia-X / Ocean C2D)
```

---

## 🧱 La Pila de Problemas e Interacción entre Capas

La composición de las tres capas acumula retos únicos:

```none
┌─────────────────────────────────────────────────────────┐
│ CAPA 4 — Gobernanza, Incentivos y Tokenomics Web3       │ ──▶ Shapley para trayectorias, Free-riding, RGPD
├─────────────────────────────────────────────────────────┤
│ CAPA 3 — Orquestación C2D sobre Ocean Protocol          │ ──▶ Encadenar jobs Docker efímeros, Hashes on-chain
├─────────────────────────────────────────────────────────┤
│ CAPA 2 — FRL Offline (Agregación de Pesimismo)         │ ──▶ Cobertura colectiva vs. Pesimismo local (★)
├─────────────────────────────────────────────────────────┤
│ CAPA 1 — Offline RL Monoagente                          │ ──▶ Distributional shift, Acciones OOD
└─────────────────────────────────────────────────────────┘
```

### ★ El Dilema Científico Core: Pesimismo Local vs. Cobertura Colectiva
- **En Offline RL monoagente (CQL)**: Se penalizan severamente las acciones que no aparecen en el dataset local para no caer en sobreestimaciones catastróficas.
- **En el setting Federado**: Una acción que para el *Cliente A* es totalmente desconocida (y por tanto su CQL la penaliza a cero) puede estar **abundantemente cubierta y demostrada por el *Cliente B***.
- Promediar ciegamente los pesimismos locales destruye el aprendizaje. El reto científico es **explotar la cobertura colectiva del Data Space** sin revelar las trayectorias de los participantes.

## ⚙️ La Infraestructura Tecnológica: Ocean Compute-to-Data (C2D)

En la práctica, cada ronda federada se ejecuta como un conjunto de trabajos de **Compute-to-Data (C2D)** sobre la red **Pontus-X**:

```none
1. El Orquestador publica la ronda t y el checkpoint del modelo global θ_t.
2. Cada participante autoriza la ejecución en su nodo mediante Data Tokens (ERC-20).
3. El contenedor C2D entrena localmente sobre el dataset estático (ej. logs de la ITV).
4. El resultado (pesos locales θ_t^k) se firma criptográficamente mediante Remote Attestation (TEE).
5. El Orquestador agrega los pesos (FedAvg/FedProx/FEDORA) y publica θ_{t+1}.
6. Todo el ciclo queda registrado inmutablemente en la blockchain para auditoría (AI Act).
```

## 🌺 Integración Arquitectónica: Ejecutar Flower (`flwr`) en Ocean C2D

El framework de Aprendizaje Federado **Flower** ([`flwrlabs/flower`](https://github.com/flwrlabs/flower)) se puede integrar perfectamente dentro de entornos **Compute-to-Data (C2D)**. Al ser un sistema basado en ejecución de contenedores Docker aislados sobre Kubernetes, existen dos patrones de diseño para orquestar Flower sobre Ocean Protocol:

```none
 PATRÓN A (gRPC Directo):
 [ Flower Server / SuperLink ] ◄── gRPC Socket (Whitelisted) ── [ C2D Pod: flwr ClientApp ] (On-Premise)

 PATRÓN B (Asíncrono por Ficheros - Zero-Trust):
 [ Orquestador ocean.py ] ──▶ Pasa θ_t en /inputs ──▶ [ C2D Pod: Entrena flwr local ] ──▶ Escribe θ_t^k en /outputs
          ▲                                                                                   │
          └────────────────── Agrega FedAvg y publica θ_{t+1} ────────────────────────────────┘
```

### Patrón A: Conexión gRPC Directa (Online ClientApp)
- **Mecanismo:** El servidor de Flower (`flwr SuperLink`) se ejecuta en una máquina pública o punto de agregación. El trabajo C2D de Ocean arranca una imagen Docker con `flwr` que actúa como cliente (`ClientApp`).
- **Requisito de Red:** El proveedor de C2D debe permitir conexiones gRPC de salida (*outbound*) hacia la IP/dominio del servidor Flower.

### Patrón B: Intercambio Asíncrono por Archivos (`/inputs` y `/outputs`) (Recomendado para Máxima Soberanía)
- **Mecanismo:** Muchos proveedores de Data Spaces industriales prohíben por completo las conexiones de red salientes desde los pods de cómputo para evitar fugas de datos.
- **Flujo de Ejecución:**
  1. Para cada ronda $t$, el script orquestador (`ocean.py`) publica el trabajo C2D pasando el archivo con los pesos del modelo global $\theta_t$ en la carpeta de entradas cifradas (`/inputs`).
  2. El contenedor C2D ejecuta un script de Flower en modo cliente local (`flwr` sobre `NumPyClient` / `ClientApp`), cargando el dataset local montado en `/data`.
  3. Tras entrenar $E$ épocas locales, el cliente guarda la actualización de pesos $\theta_t^k$ en la carpeta de salida (`/outputs`).
  4. El microservicio Ocean Provider firma criptográficamente los resultados en `/outputs` y los expone únicamente al orquestador autorizado.
  5. El servidor Flower agrega las actualizaciones retenidas de todos los clientes ($\theta_{t+1} = \text{FedAvg}(\{\theta_t^k\})$) y lanza la ronda $t+1$.

> **Ventaja de esta integración:** Combina la simplicidad de la API de Flower con la garantía criptográfica y de soberanía estricta de Ocean C2D / Pontus-X sin necesidad de abrir puertos de red.

## 🏥 Casos de Uso Industriales Ancla

- **Inspección Técnica de Vehículos (ITV)**: Predecir fallos críticos en dirección/frenos analizando logs históricos de inspecciones sin compartir datos de clientes entre estaciones competidoras.
- **Salud (EHDS - European Health Data Space)**: Ajustar regímenes de tratamiento dinámico (DTR) para pacientes críticos combinando historiales de hospitales de distintos países europeos.
- **Energía y Smart Grids**: Optimizar la gestión de micro-redes de energía distribuidas sin exponer hábitos de consumo ni datos comerciales de las comercializadoras.

## 🧪 Práctica recomendada para el Proyecto

- [ ] **Prototipo C2D local:** Desplegar `oceanprotocol/barge` localmente y ejecutar un script simple de PyTorch/Scikit-learn como trabajo C2D usando `ocean.py`.
- [ ] **Flower en contenedor C2D:** Crear una imagen Docker con `flwr` que lea los parámetros globales de `/inputs` y escriba los parámetros locales entrenados en `/outputs`.
- [ ] **Publicación en Pontus-X Devnet:** Crear un dataset simulado de inspecciones de ITV, registrarlo en la red Devnet de Pontus-X mediante `ocean.py` y solicitar la ejecución de una ronda de entrenamiento federado.
- [ ] **Simulación FRL Offline:** Implementar una prueba de concepto combinando Flower con pesimismo CQL (`d3rlpy`) ejecutado sobre nodos C2D aislados.
