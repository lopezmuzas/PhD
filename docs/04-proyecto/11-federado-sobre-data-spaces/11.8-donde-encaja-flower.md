# 11.8 Dónde encaja Flower

Este laboratorio se llama "Flower + Ocean C2D" y **no usa Flower**. Es una
decisión deliberada y hay que justificarla, porque el documento original si lo
importaba.

---

## Que hacia el código original

```python
import flwr as fl

class OceanFlowerClient(fl.client.NumPyClient):
    def fit(self, parameters, config):
        ...

if __name__ == "__main__":
    client = OceanFlowerClient(...)
    updated_weights, num_samples, metrics = client.fit(
        parameters=client.get_parameters(config={}), config={}
    )
```

Importaba `flwr`, heredaba de `NumPyClient`... y luego llamaba a `.fit()` a
mano. **Eso no es Flower.** Es FedAvg artesanal con forma de Flower.

Falta todo lo que Flower realmente aporta:

| Pieza de Flower | Estaba? |
|-----------------|---------|
| `start_client()` / transporte gRPC | no |
| `Strategy` (FedAvg, FedProx, FedAdam...) | no |
| Gestion de rondas por el servidor | no |
| Seleccion y muestreo de clientes | no |
| Serialización `Parameters`/`ndarrays` | no |

Quedaba una dependencia de ~50 MB que aportaba una clase base vacía. El
resultado es peor que no usarla: **parece** que tienes la robustez de un
framework probado y no la tienes.

---

## Por que Flower no puede funcionar dentro de C2D

No es cuestion de gusto. Flower es un sistema **cliente-servidor sobre gRPC**:
el cliente abre una conexión saliente al servidor y mantiene un canal
bidireccional durante todas las rondas.

Dentro de un contenedor C2D:

```javascript
// ocean-node/src/components/c2d/compute_engine_docker.ts
if (!env.enableNetwork) {
  hostConfig.NetworkMode = 'none'
}
```

**No hay pila de red.** El `connect()` de Flower falla antes de la primera
ronda. Y aunque el operador activase `enableNetwork`, seguirian sobrando dos
problemas:

1. **El modelo de ejecución no encaja.** Un job C2D es un proceso efimero de una
   sola ejecución: arranca, corre, muere, y el nodo recoge `/data/outputs`. Un
   cliente Flower es un proceso de larga vida que participa en N rondas. Meter
   Flower dentro obligaria a que un solo job durase todo el entrenamiento, con
   el nodo del proveedor manteniendo una conexión saliente hacia ti durante
   horas: exactamente lo que un proveedor zero-trust no va a permitir.
2. **Abrir la red destruye la propuesta de valor.** Todo el argumento de C2D es
   que el algoritmo esta encerrado y no puede exfiltrar datos. Un algoritmo con
   socket saliente puede mandarse el dataset entero a si mismo.

**El patrón asíncrono por ficheros no es un apano: es la única arquitectura
compatible con la garantía que vende C2D.**

---

## Que nos habriamos llevado de Flower

Honestamente, poco para este caso:

| | Flower | Aquí |
|---|--------|------|
| Transporte | gRPC | imposible (sin red) |
| Estrategias | FedAvg, FedProx, FedAdam, Krum... | `fedavg()`, 6 líneas |
| Simulación | `flwr.simulation` con Ray | `simulate.py`, 20 líneas |
| Serialización | `Parameters` | `serialization.py`, sin pickle |
| Peso | ~50 MB + dependencias | 0 |

Su catalogo de estrategias es lo único realmente valioso. Y es fácil de
aprovechar sin adoptar el framework:

```python
from flwr.server.strategy.aggregate import aggregate   # FedAvg ponderado
new_params = aggregate([(params, n) for params, n in updates])
```

Elegimos no hacerlo por dos motivos: es API semi-interna que puede cambiar sin
aviso, y son seis líneas que **podemos testear**
(`test_fedavg_pondera_por_muestras`). En un laboratorio de aprendizaje, ver el
FedAvg escrito vale más que importarlo.

---

## El mapeo conceptual

Si vienes de Flower, esto es lo mismo con otros nombres:

| Flower | Aquí | Fichero |
|--------|------|---------|
| `NumPyClient.get_parameters()` | `Learner.get_params()` | `ports.py` |
| `NumPyClient.set_parameters()` | `Learner.set_params()` | `ports.py` |
| `NumPyClient.fit()` | `run_local_round()` | `domain/round.py` |
| `NumPyClient.evaluate()` | `Learner.evaluate()` | `learners/` |
| `Strategy.aggregate_fit()` | `fedavg()` | `domain/aggregation.py` |
| `ServerConfig(num_rounds=N)` | bucle de `run_federated()` | `ocean/orchestrator.py` |
| Transporte gRPC | ficheros en `/data` + API HTTP | `adapters/stores.py` |
| `FitIns.config` | `algoCustomData["config"]` | `config.py` |

Las abstracciones son deliberadamente **isomorfas** a las de Flower. Cuando
migres, la traduccion es mecanica.

---

## Cuando SI usar Flower

Flower es excelente. Uselo cuando:

- **Los clientes puedan abrir conexiones salientes.** Despliegues federados
  clasicos (moviles, sucursales, hospitales con un agente instalado) donde
  controlas ambos extremos.
- **Quieras el catalogo de estrategias** sin reimplementarlas.
- **Necesites simulación a escala.** `flwr.simulation` con Ray maneja cientos de
  clientes virtuales; nuestro `simulate.py` es un bucle `for`.
- **El entrenamiento sea de larga duracion** con clientes persistentes.

C2D es el caso raro donde no encaja. La mayoria de despliegues federados no son
C2D.

### Ruta de migracion

Si algún día mueves esto a Flower, el dominio no se toca. Escribes un adaptador
nuevo:

```python
import flwr as fl
from fedlab.domain.round import run_local_round

class FlowerAdapter(fl.client.NumPyClient):
    """Adaptador: traduce el protocolo de Flower a nuestros puertos."""

    def __init__(self, source, learner, cfg):
        self.source, self.learner, self.cfg = source, learner, cfg

    def get_parameters(self, config):
        return self.learner.get_params()

    def fit(self, parameters, config):
        store = InMemoryStore(initial=parameters)
        result = run_local_round(store, self.source, self.learner, self.cfg)
        return result.params, result.num_samples, result.metrics

    def evaluate(self, parameters, config):
        self.learner.set_params(parameters)
        X, y = self.source.load()
        m = self.learner.evaluate(X, y)
        return m["loss"], len(X), m
```

Unas veinte líneas en `adapters/`. `domain/`, `learners/` y los tests siguen
igual.

**Ese es el argumento entero de la arquitectura hexagonal:** el framework de
transporte es un detalle intercambiable, no el centro del sistema. El documento
original tenía a Flower en el centro y los datos en la periferia. Aquí es al
reves.
