# 11.1 Visión general y arquitectura

## El problema

Un proveedor de datos (hospital, banco, fabrica) tiene datos que no puede
compartir. Tú quieres entrenar un modelo con ellos. El aprendizaje federado
invierte el flujo: en vez de mover los datos al modelo, **mueves el modelo a
los datos**.

Cada ronda:

1. El orquestador envia los pesos globales `theta_t` a cada proveedor.
2. Cada proveedor entrena en local y devuelve `theta_t^k`. **Los datos no se mueven.**
3. El orquestador promedia: `theta_{t+1} = sum_k (n_k / n) * theta_t^k`.

Eso es FedAvg. Todo lo demas de este laboratorio es fontaneria para ejecutar el
paso 2 dentro de la infraestructura de otra persona.

---

## Por que el patrón asíncrono por ficheros

La solución "natural" sería Flower: un servidor gRPC al que se conectan los
clientes. **No funciona en C2D**, y no por gusto arquitectónico.

Lo verifiqué en el código de ocean-node (`compute_engine_docker.ts`):

```javascript
if (!env.enableNetwork) {
  hostConfig.NetworkMode = 'none'   // sin red dentro del contenedor
}
```

El contenedor arranca **sin pila de red** salvo que el operador del nodo active
`enableNetwork` en ese entorno de computo. No hay `localhost`, no hay DNS, no
hay socket saliente. Un cliente Flower moriría en el `connect()`.

Además corre con `CapDrop: ALL`, `no-new-privileges` y un UID no-root. El diseño
de C2D asume que **el algoritmo es hostil**. Trátalo como tal desde el principio.

Así que el único canal de comunicación son los ficheros:

```
  Orquestador (tu máquina)          ocean-node (servidor del proveedor)        Contenedor (sin red)
 ──────────────────────────        ────────────────────────────────────       ──────────────────────
 1. theta_t -> algoCustomData ──▶  2. escribe /data/inputs/                ──▶ 3. arranca el entrypoint
                                      algoCustomData.json                      4. lee theta_t
                                      + descarga el dataset                    5. entrena sobre /data/inputs
                                                                               6. escribe /data/outputs
 8. descarga y desempaqueta   ◄──  7. empaqueta /data/outputs en un tar   ◄──
 9. FedAvg -> theta_{t+1}
```

**Una ronda federada = un job C2D por proveedor.** El estado vive en el
orquestador; el contenedor es puro, efimero y sin memoria entre rondas.

---

## Como viajan los pesos: el detalle que se suele romper

Esta es la pieza que falta en la mayoria de guias. El contenedor necesita
recibir `theta_t`, pero no tiene red y el dataset lo monta el nodo. Hay tres
vias:

| Via | Como | Cuando usarla |
|-----|------|---------------|
| **`algoCustomData`** | JSON que el nodo escribe en `/data/inputs/algoCustomData.json` en **cada job** | **Labs 0-3.** Modelos pequeños. Sin republicar nada |
| Asset adicional | Publicas los pesos como asset nuevo cada ronda y lo pasas en `datasets` | Produccion, modelos grandes. Correcto pero lento y caro |
| Bucket externo | El contenedor lee de S3 | **Rompe el zero-trust.** Exige red. Evitar |

Verificado en `compute_engine_docker.ts`: el nodo escribe `algoCustomData.json`
**siempre**, aunque este vacío (`{}`). Por eso la ronda 0 funciona sin caso
especial: `load_global()` devuelve `None` y el modelo entrena desde su
inicializacion.

Un modelo de 6 parámetros ocupa ~200 bytes en JSON. Uno de 100.000 ocupa ~2 MB y
ya no cabe: por eso `serialization.check_json_size()` falla pronto y con un
mensaje que te dice que hacer.

## La arquitectura: puertos y adaptadores

El objetivo de diseño es que **el mismo código de entrenamiento corra en los
cuatro labs sin tocarse**. Eso obliga a invertir la dependencia en la frontera
de I/O.

```
                    ┌─────────────────────────────┐
                    │        domain/              │
   adapters/  ────▶ │  round.py  aggregation.py   │ ◀────  entrypoints/
   (todo el I/O)    │  datasets.py                │        (composition root)
                    │                             │
                    │  cero os, cero requests     │
                    │  cero Ocean, cero Docker    │
                    └─────────────────────────────┘
                              ▲
                              │ define
                        ports.py (Protocol)
```

## SOLID, sin ceremonia

| Principio | Donde se ve |
|-----------|-------------|
| **SRP** (el que te importa) | `aggregation.py` solo promedia. `round.py` solo orquesta una ronda. `stores.py` solo hace I/O. Ninguno hace dos cosas |
| **OCP** | Cambiar FedAvg por FedProx = añadir una funcion en `aggregation.py`. El bucle no se toca. `ex03` ya lo demuestra: `federated(partitions, aggregator)` recibe la estrategia como argumento |
| **LSP** | `test_el_dominio_funciona_con_cualquier_store` ejecuta el mismo caso de uso con `InMemoryStore` y `FileStore` sin cambiar una línea |
| **ISP** | Puertos de 2-4 métodos. Nada de una clase base con 15 |
| **DIP** | Las flechas apuntan hacia dentro. `domain/` no importa `os` |

Y KISS donde más se nota: **NumPy puro, sin PyTorch**. La imagen baja de ~2 GB a
~150 MB, arranca sin red y los tres ejemplos corren en segundos. PyTorch es una
extensión documentada, no una dependencia.

---

## Lo que este diseño NO resuelve

Se honesto en la memoria del proyecto:

- **FedAvg no es privado.** Los pesos filtran información sobre los datos de
  entrenamiento (ataques de inversion de gradientes). "Los datos no salen" es
  cierto; "no se filtra nada" no lo es. Si el argumento comercial es la
  privacidad, hace falta privacidad diferencial o agregación segura.
- **No hay defensa contra proveedores maliciosos.** Un nodo puede enviar pesos
  envenenados y FedAvg los promedia sin rechistar. Existen agregadores robustos
  (Krum, mediana coordenada) y encajan en `aggregation.py` sin tocar nada más.
- **No hay verificación de que el proveedor ejecuto lo que dijo.** Eso es
  atestacion remota, y es un problema abierto.
