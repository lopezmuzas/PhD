# 11.0 Por qué existe esta sección

> **Qué responde:** ¿qué problema real hay detrás de todo esto, qué es
> exactamente el código de `labs/`, y para qué sirve?

Empieza por aquí. Las páginas siguientes asumen que ya sabes por qué estás
montando esto; esta no asume nada.

---

## 1. El problema, con números

Tres hospitales estudian la misma patología. Uno tiene 110 casos registrados,
otro 60, el tercero 30.

El tercero **no puede entrenar nada útil**: con 30 ejemplos, cualquier modelo
que ajuste sobreajusta. Lo racional sería juntar los 200 casos y entrenar una
vez. Pero los datos clínicos no se pueden mover: hay una normativa que lo
impide, y aunque no la hubiera, ninguna de las tres organizaciones se fía lo
suficiente de las otras.

Ese es el problema entero. Y no es un ejemplo de manual: es la situación por
defecto en sanidad, banca, industria y administración pública.

```none
   Hospital A          Hospital B          Hospital C
   n = 110             n = 60              n = 30
      │                   │                   │
      └── no puede ───────┴─── compartir ─────┘
                          │
                          ▼
              ¿cómo entrenan un modelo juntos?
```

---

## 2. Dos tecnologías que resuelven mitades distintas

Aquí se confunden constantemente, y separarlas aclara muchísimo.

| | Qué resuelve | Qué **no** resuelve |
|---|---|---|
| **Aprendizaje federado** | El **algoritmo**: cómo entrenar un modelo sin juntar los datos | Quién tiene permiso para hacerlo, con qué contrato y con qué trazabilidad |
| **Data spaces** (Gaia-X, IDSA, Ocean) | La **gobernanza**: identidad, permisos, contratos de uso, auditoría | Cómo se entrena realmente el modelo |

Federado sin gobernanza es un acuerdo informal entre gente que ya se conoce.
Gobernanza sin federado es un catálogo precioso de datos que nadie puede usar.

**Esta sección junta las dos**, que es donde empiezan los problemas interesantes
y donde vive el proyecto de tesis (→ 1.5, eje ③).

### Aprendizaje federado en tres líneas

En vez de mover los datos al modelo, **mueves el modelo a los datos**. Cada
ronda:

1. Envías los pesos actuales a cada participante.
2. Cada uno entrena con **sus** datos y te devuelve solo los pesos resultantes.
3. Promedias los pesos, ponderando por cuántos datos tenía cada uno.

Eso es **FedAvg**, y es todo el algoritmo. Los datos nunca se mueven.

### Compute-to-Data en tres líneas

C2D es la respuesta de Ocean Protocol a "¿cómo dejo que alguien use mis datos
sin dárselos?". El proveedor publica un dataset que **nunca se descarga**. Tú
envías un **algoritmo empaquetado en un contenedor Docker**. El nodo del
proveedor lo ejecuta junto a los datos, en su máquina, y te devuelve únicamente
lo que el algoritmo haya escrito en la carpeta de salida.

Es una inversión limpia: el código viaja, los datos no.

---

## 3. Por qué juntarlas no es obvio

Aquí está el hallazgo que justifica que esta sección exista en vez de ser un
párrafo en otra página.

**El manual dice:** usa Flower. Levantas un servidor, los clientes se conectan
por gRPC, el framework se encarga del resto.

**El manual no funciona.** Verificando el código fuente de `ocean-node`, el
contenedor de C2D arranca **sin pila de red** salvo que el operador del nodo
active explícitamente esa opción. No hay `localhost`, no hay DNS, no hay socket
saliente. Un cliente Flower moriría en la primera llamada a `connect()`.

Y no es un descuido: el contenedor corre además con todas las capacidades
retiradas, sin escalada de privilegios y con un usuario no-root. **El diseño de
C2D asume que tu algoritmo es hostil.** Es coherente: el proveedor te está
dejando ejecutar código sobre datos que no puedes ver.

Consecuencia directa:

```none
Federado "de libro"          Federado sobre C2D
─────────────────────        ──────────────────────────────
servidor + clientes          orquestador + N jobs independientes
conexión persistente         sin conexión: solo ficheros
una ronda = una sesión       una ronda = N jobs C2D
el estado vive en el server  el contenedor no recuerda nada
```

**Una ronda federada = un job C2D por proveedor.** El contenedor es puro,
efímero y sin memoria entre rondas. Todo el estado vive en tu orquestador.

Esa restricción es la que da forma a todo el código de `labs/`. No es una
preferencia arquitectónica: es lo único que funciona. (El razonamiento completo,
en → 11.8.)

## 4. Qué es exactamente `labs/flower-ocean-c2d/`

**No es una demo.** Es un paquete de Python con tests, pensado para que crezcan
encima los experimentos de la tesis.

```none
labs/flower-ocean-c2d/
├── src/fedlab/
│   ├── ports.py        ← los 3 contratos. Todo lo demás depende de esto
│   ├── domain/         ← FedAvg, la ronda local, los datasets
│   │                     CERO I/O · CERO Ocean · CERO Docker
│   ├── learners/       ← los modelos (NumPy puro)
│   ├── adapters/       ← TODO el I/O vive aquí
│   │                     InMemory | Ficheros | C2D
│   └── entrypoints/    ← el único sitio que sabe de Ocean
├── examples/           ← los tres experimentos
├── tests/              ← 38 tests, menos de 2 segundos
└── docker/             ← la imagen que se envía al nodo
```

**La regla que lo ordena todo:** las dependencias apuntan hacia dentro. El
paquete `domain/` no importa `os`, ni `requests`, ni nada de Ocean. Ocean es un
detalle de infraestructura, no el centro del diseño.

### Por qué esa regla importa aquí más que en otros proyectos

Porque permite que **el mismo código de entrenamiento** corra en cuatro entornos
distintos cambiando una sola pieza:

| Entorno | Adaptador de almacenamiento |
|---|---|
| En memoria, sin nada más | `InMemoryStore` |
| Carpetas locales que imitan `/data` | `FileStore` |
| Dentro de un contenedor Docker | `FileStore` con las rutas de C2D |
| Contra un `ocean-node` real | `C2DStore` |

Sin esa separación, probar el algoritmo exigiría tener un nodo Ocean levantado.
Con ella, los 38 tests corren en dos segundos en tu portátil.

## 5. Los tres objetivos

### ① Entender (didáctico)

Que el federado sobre data spaces deje de ser un diagrama de una presentación y
pase a ser algo que has visto fallar y arreglar.

### ② Tener un banco de pruebas (instrumental)

Un sitio donde probar ideas de la tesis con ciclos de segundos, no de horas.
Cambiar el reparto de datos, meter un participante malicioso, sustituir FedAvg
por FedProx: todo eso son cambios de una tarde sobre esta base.

### ③ Desriesgar la infraestructura (estratégico)

**El más importante.** Descubrir que el contenedor no tiene red es barato ahora
y carísimo dentro de un año, con los experimentos a medias y una fecha encima.

Esta sección existe, en buena medida, para que las sorpresas de infraestructura
aparezcan **antes** de que la tesis dependa de ellas.

---

## 6. Por qué cuatro laboratorios y no un tutorial

Un pipeline federado sobre C2D junta cuatro tecnologías a la vez: aprendizaje
federado, Docker, la API de un nodo Ocean y criptografía de firmas.

Si lo montas todo de golpe y falla —y va a fallar— **no sabes cuál de las cuatro
capas falló**. Puedes perder días depurando el algoritmo cuando el problema era
la arquitectura de la imagen Docker.

Es el mismo principio de aislamiento de variables de → 3.8: cambia una cosa cada
vez.

| Lab | Añade | Deja de ser sospechoso | Tiempo |
|---|---|---|---|
| **0** | El aprendizaje federado | — | 2 min |
| **1** | El patrón de ficheros | la lógica federada | 5 min |
| **2** | Docker | el contrato de ficheros | 15 min |
| **3** | `ocean-node` | la imagen | tu servidor |

El código de entrenamiento es **idéntico en los cuatro**. Cuando el Lab 3 falle,
ya sabrás con certeza que el problema es de infraestructura, porque todo lo
demás ya lo viste funcionar.

## 7. Qué demuestran los tres ejemplos

No son ilustraciones: cada uno responde a una pregunta concreta.

### `ex01` — ¿funciona esto siquiera?

Regresión lineal, `y = 3x + 2`, dos parámetros. Tres nodos que ven **tramos
disjuntos del eje X**: ninguno puede estimar bien la recta en solitario.

Puedes leer la convergencia a ojo, y por eso es el primero: si esto no converge,
hay un bug, no un fenómeno.

### `ex02` — ¿en qué me puedo equivocar? ⭐

**El más importante de los tres, y el más incómodo.**

Girando la heterogeneidad de los datos entre nodos, la **accuracy apenas se
mueve** mientras la **divergencia entre modelos locales se multiplica por 9**.

La razón: la regresión logística es convexa, así que promediar soluciones
locales sigue cayendo cerca del único mínimo. **Una red profunda no tiene esa
garantía.**

La lección, que vale para toda la tesis:

> Si tu prueba de concepto usa un modelo lineal y funciona, **todavía no has
> probado nada** sobre la red profunda que quieres desplegar. Y si solo miras la
> accuracy, no verás venir el problema.

Es exactamente la misma advertencia que → 1.6 hace sobre el RL offline
federado: promediar cosas entrenadas sobre datos distintos no significa lo que
parece.

### `ex03` — ¿merece la pena tanta infraestructura?

Los tres hospitales del principio. El pequeño pasa de **0,647 a 0,922 de
accuracy** sin mover un solo dato, y el federado **alcanza el techo del
centralizado**.

Esta es la tabla que justifica el proyecto ante un comité. Si el federado no
superase claramente al "solo local", no habría ningún motivo para montar nada de
esto.

## 8. Cómo está montado, en una idea

El código **no está pegado dentro del Markdown**. Vive en `labs/`, fuera de la
carpeta de documentación, y las páginas lo incluyen por referencia.

```none
docs/11-.../*.md  ──── incluye ────▶  labs/flower-ocean-c2d/src/...
       │                                        │
       │                                        ├─ make test  (¿funciona?)
       └─ mkdocs build --strict ────────────────┘
              (¿los enlaces y los includes resuelven?)
```

**Por qué importa:** un bloque de código dentro de un `.md` no se ejecuta, no se
testea, y no se entera de que el código real ha cambiado. Es una copia que
empieza a mentir el día que alguien refactoriza.

Con este montaje, si alguien rompe `fedavg()`, los tests fallan y la
documentación **no puede** seguir mostrando la versión buena, porque no tiene
copia propia.

El detalle de configuración está en → 11.10.

## 9. Qué NO es esto

Decirlo evita expectativas equivocadas:

- **No es un producto.** No hay autenticación de usuarios, ni reintentos serios,
  ni tolerancia a fallos.
- **No es privacidad garantizada.** Compartir pesos **no** equivale a no filtrar
  nada: existen ataques de reconstrucción a partir de gradientes. La privacidad
  diferencial es un paso posterior, no algo que ya esté hecho.
- **No usa modelos profundos.** Los learners son NumPy puro, a propósito, para
  que el ruido del framework no tape el fenómeno que se quiere ver.
- **No está probado contra un nodo real.** Lo que está verificado y lo que no
  está en la tabla del → 11-índice. Léela antes de fiarte de nada.

## 10. Qué deberías saber hacer al terminar

- Explicar por qué C2D obliga al patrón asíncrono por ficheros, y a quién le
  importa eso.
- Ejecutar una ronda federada completa contra un nodo real, y depurarla cuando
  falle.
- Reconocer que la accuracy puede estar ocultándote un problema de deriva.
- Sustituir el modelo, el agregador o el almacenamiento sin tocar el resto.
- Decidir con criterio si tu caso necesita Flower o no.
