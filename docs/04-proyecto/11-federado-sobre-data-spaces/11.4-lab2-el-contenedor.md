# 11.4 Lab 2 · El contenedor

**Objetivo:** que la imagen cumpla el contrato de C2D. Cambia **una** cosa: el
código se ejecuta dentro de Docker con las rutas reales de Ocean.

Sigue sin haber ocean-node.

```bash
make docker-build
make lab2
```

## El test que te ahorra las tardes

Antes de tocar Docker, hay ocho tests que verifican el contrato **sin Docker y
sin nodo**, montando un `/data` falso identico al que crea ocean-node:

```bash
pytest tests/test_c2d_contract.py -m "not docker"
```

```
test_encuentra_el_dataset_ignorando_algocustomdata     PASSED
test_algocustomdata_vacio_no_rompe_nada                PASSED
test_algocustomdata_corrupto_no_tumba_el_job           PASSED
test_lee_los_pesos_globales_de_algocustomdata          PASSED
test_entrypoint_produce_los_ficheros_esperados         PASSED
test_entrypoint_continua_desde_los_pesos_recibidos     PASSED
test_falla_con_codigo_2_si_no_hay_dataset              PASSED
test_modelo_desconocido_falla_ruidosamente             PASSED
```

Y luego el mismo contrato contra la imagen real:

```python
@pytest.mark.docker
def test_imagen_docker_cumple_el_contrato(tmp_path):
    data = build_fake_data_dir(tmp_path)
    proc = subprocess.run([
        "docker", "run", "--rm", "--network", "none",   # <- como el nodo real
        "-v", f"{data}:/data",
        "-e", "FL_MODEL=logistic", "-e", "FL_FEATURES=6",
        "fedlab:test",
    ], capture_output=True, text=True)
    assert proc.returncode == 0
    assert (data / "outputs" / "update.npz").exists()
```

Fijate en `--network none`: reproduce exactamente lo que hace ocean-node. Si tu
código intenta salir a Internet, **falla aquí**, en un segundo, en vez de en un
job remoto con un estado 41 opaco.

### El test más importante de los ocho

```python
def test_entrypoint_continua_desde_los_pesos_recibidos(tmp_path):
    fresh = build_tmp_run(tmp_path / "a", custom={})
    warm  = build_tmp_run(tmp_path / "b", custom={"params": [...]})
    assert not np.allclose(fresh[0], warm[0])
```

Comprueba que **los pesos que entran afectan a los que salen**. Si esto falla,
cada ronda entrena desde cero y no hay federación: solo N entrenamientos
aislados repetidos, con una curva de perdida que parece razonable y un modelo
que no aprende nada colectivo. Es el bug más caro del pipeline y el más difícil
de ver a simple vista.

## El Dockerfile

```dockerfile
FROM python:3.12-slim

COPY requirements.txt /tmp/requirements.txt
RUN pip install --no-cache-dir -r /tmp/requirements.txt && rm /tmp/requirements.txt

WORKDIR /app
COPY src/ /app/src/
ENV PYTHONPATH=/app/src PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1

RUN chmod -R a+rX /app

ENV FL_ENV=c2d FL_MODEL=logistic FL_FEATURES=6
ENTRYPOINT ["python", "-m", "fedlab.entrypoints.client_main"]
```

Cinco decisiones que importan:

**1. `--platform linux/amd64`, siempre.**

```bash
docker buildx build --platform linux/amd64 -t tu-usuario/fedlab:v1 -f docker/Dockerfile .
```

ocean-node valida la arquitectura del manifiesto (`checkManifestPlatform`). Una
imagen `arm64` construida en un Mac muere en un nodo `amd64` con un estado 11 o
22 y ningún mensaje util. **Es el fallo número uno.**

**2. El código va a `/app`, nunca a `/data`.** El nodo monta un volumen en
`/data` y machaca lo que hubiera ahí.

**3. No declaramos `USER`.** El nodo impone su propio UID/GID
(`C2D_CONTAINER_UID`/`GID`), con `CapDrop: ALL` y `no-new-privileges`. Solo
garantizamos que el código sea legible por cualquiera (`chmod a+rX`).

**4. `PYTHONUNBUFFERED=1`.** Sin esto, si el proceso muere, Python se lleva el
buffer de stdout a la tumba y `/data/logs/algorithm.log` sale vacío. Sin shell y
sin red dentro del contenedor, **ese log es tu única ventana**.

**5. Dependencias antes que código.** Capa cacheada: tocar el código no
reinstala NumPy.

## Por que NumPy y no PyTorch

| | NumPy | PyTorch |
|---|---|---|
| Tamano de imagen | ~150 MB | ~2 GB |
| `docker pull` en el nodo | segundos | minutos, **en cada job** |
| Riesgo de timeout en estado 10 | bajo | alto |

En un bucle federado el nodo hace pull en **cada ronda y cada proveedor**. Con
tres nodos y cinco rondas son quince pulls. La diferencia entre 150 MB y 2 GB
deja de ser estetica.

Para los tres ejemplos de este laboratorio, PyTorch no aporta nada: una
regresión logística en NumPy son 20 líneas y se entiende entera.

**Cuando lo necesites de verdad** (redes profundas), instala la rueda CPU y fija
las versiones:

```dockerfile
RUN pip install --no-cache-dir \
      --index-url https://download.pytorch.org/whl/cpu \
      torch==2.5.1
```

Sin `--index-url` te bajas CUDA entero: ~2 GB de GPU que el nodo no va a usar.

## Publicar la imagen

El nodo hace `docker pull`. **Una imagen que solo existe en tu portátil no
sirve.**

```bash
docker tag fedlab:test tu-usuario/fedlab:v1
docker push tu-usuario/fedlab:v1
make docker-digest        # -> tu-usuario/fedlab@sha256:abc123...
```

Usa el **digest**, no el tag, en el job C2D:

```python
AlgorithmSpec(image="tu-usuario/fedlab", tag="v1", checksum="sha256:abc123...")
```

Un tag es mutable: `v1` puede apuntar a otra cosa mañana y tu experimento deja
de ser reproducible sin que te enteres. El digest fija los bytes exactos. En
ocean-node, `getAlgorithmImage()` compone `image@checksum` cuando das checksum, y
`image:tag` cuando no.
