# 3.6 Escalar: de una GPU a muchas

> **Qué responde:** ¿qué cambia realmente al pasar de una GPU a muchas, y qué se
> rompe por el camino?

> **Ubicación en el mapa:** esta página es el eje ③ de → 1.5 en su versión
> "fácil": datos distribuidos dentro de una **misma organización**, con red
> rápida y control total. El salto conceptual a federado y data spaces viene
> después, y buena parte de sus problemas se entienden mejor habiendo visto
> primero lo que ya cuesta aquí.

---

## Las tres cosas que se pueden repartir

```none
              ┌──────────────────────────────────────┐
              │  ¿Qué no cabe o qué va lento?        │
              └──────────────────────────────────────┘
                 │              │              │
        el DATASET      el MODELO       la SECUENCIA
                 │              │              │
                 ▼              ▼              ▼
        Paralelismo de   Paralelismo de   Paralelismo de
             datos        modelo/tensor      contexto
        (DDP, FSDP)      (TP, PP, MoE)
```

| Estrategia | Qué reparte | Cuándo |
|---|---|---|
| **Datos (DDP)** | Los lotes. Cada proceso tiene el modelo entero | El modelo cabe en una GPU. **El 95 % de los casos** |
| **Datos + estados (ZeRO / FSDP)** | Además, gradientes, estados del optimizador y pesos | El modelo cabe justo o no cabe |
| **Tensor (TP)** | Las matrices dentro de una capa | Capas individuales enormes. Requiere red muy rápida |
| **Pipeline (PP)** | Grupos de capas entre nodos | Modelos muy profundos; introduce burbujas de inactividad |

**Regla práctica:** empieza siempre por DDP. Solo pasa a FSDP cuando la memoria
lo obligue, y a TP/PP cuando FSDP ya no baste. Cada nivel añade complejidad de
depuración desproporcionada.

---

## Paralelismo de datos, en detalle

Cada proceso tiene una réplica completa del modelo, procesa un trozo distinto del
lote, y al final del backward se **promedian los gradientes** entre todos
(`all-reduce`). Todos los procesos aplican la misma actualización, así que las
réplicas permanecen idénticas.

```none
proceso 0 ── lote A ──▶ grad_0 ─┐
proceso 1 ── lote B ──▶ grad_1 ─┤
proceso 2 ── lote C ──▶ grad_2 ─┼──▶ all-reduce ──▶ grad promedio ──▶ update
proceso 3 ── lote D ──▶ grad_3 ─┘
```

**Consecuencia inmediata y la fuente de casi todos los errores:**

```none
lote efectivo = lote_por_proceso × nº_procesos × pasos_de_acumulación
```

Si pasas de 1 GPU a 8 sin tocar nada, has multiplicado el lote por 8. Y por
→ 3.1 y → 3.3, eso obliga a re-ajustar la tasa de aprendizaje. **Un experimento
que "empeora al escalar" casi siempre es esto y no otra cosa.**

---

## Lo que se rompe al escalar

| Qué se rompe | Por qué | Solución |
|---|---|---|
| **BatchNorm** | Calcula estadísticas sobre el lote **local**, no el global. Con lote local pequeño, las estadísticas son ruidosas y distintas en cada proceso | `SyncBatchNorm`, o cambiar a GroupNorm / LayerNorm (→ 3.4) |
| **La tasa de aprendizaje** | El lote efectivo se multiplicó | Escalado lineal + warmup (→ 3.3) |
| **El logging** | Los N procesos escriben a la vez | Registrar solo desde el proceso 0 |
| **Las métricas** | Cada proceso ve una parte de la validación | Agregar entre procesos (`all_gather`); TorchMetrics lo hace |
| **Los checkpoints** | Con FSDP los pesos están repartidos | Consolidar al guardar, o usar checkpoints distribuidos |
| **La aleatoriedad** | Misma semilla en todos los procesos → mismos datos | Semilla distinta por rango; `DistributedSampler` con `set_epoch()` |
| **El shuffling** | Sin `set_epoch()`, todas las épocas ven el mismo orden | Llamarlo explícitamente cada época |
| **La reproducibilidad** | El orden del `all-reduce` no es determinista | Asumirlo y reportar intervalos (→ 3.9) |

> **El bug silencioso número uno:** olvidar `sampler.set_epoch(epoch)`. No falla,
> no avisa, y el modelo ve exactamente el mismo orden de datos en cada época.

---

## Comunicación: dónde se pierde la escalabilidad

El `all-reduce` mueve un volumen proporcional al número de parámetros **en cada
paso**. Si la red es lenta respecto al cómputo, añadir GPUs deja de ayudar.

| Situación | Efecto |
|---|---|
| Una máquina, NVLink | Comunicación casi gratis; escalado cercano al lineal |
| Varias máquinas, InfiniBand | Buena escalabilidad con solapamiento comunicación/cómputo |
| Varias máquinas, Ethernet estándar | La comunicación domina; el escalado se estanca pronto |

Mitigaciones: solapar comunicación con backward (DDP lo hace por defecto),
*bucketing* de gradientes, acumulación de gradiente para reducir la frecuencia de
sincronización, y compresión de gradientes.

**Eficiencia de escalado**, la métrica que importa:

```none
eficiencia = (throughput con N GPUs) / (N × throughput con 1 GPU)
```

Por debajo de ~0,8 conviene entender por qué antes de añadir más hardware.

## Del clúster al federado

Aquí está el puente con tu tesis. Comparado con lo anterior, el federado
(→ 1.5, eje ③) cambia cuatro supuestos de golpe:

| Supuesto en un clúster | Qué pasa en federado |
|---|---|
| Los datos son IID entre procesos (tú los repartes) | **Cada silo tiene su distribución**; el promedio de gradientes deja de ser un gradiente insesgado del objetivo global |
| Se sincroniza cada paso | Se sincroniza cada **ronda** de muchos pasos locales (FedAvg) |
| La red es rápida y fiable | Ancho de banda escaso, participantes que se caen |
| Puedes mirar todos los datos | No puedes ver nada ajeno |

**FedAvg es, literalmente, paralelismo de datos con sincronización infrecuente y
datos no-IID.** Entender bien esta página hace que la literatura de federado se
lea mucho más rápido: casi todos sus algoritmos son correcciones a uno de esos
cuatro supuestos rotos.
